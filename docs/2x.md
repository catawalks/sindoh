# Sindoh 2X: the stock machine

**Source:** the owner's 3DWOX 2X, surveyed on 2026-11-28 with the survey
stick (v1.2, read-only) and reads over the stick's remote shell
(files copied, registers and the device tree read; no bus probed).
Nothing on the printer was changed. The survey text and the copied
scripts stay on the owner's PC (`2x_files/`); they are Sindoh's and are
not published. Inferences are marked "(our reading)". The board itself
and its factory SD card are described in [prime_sd.md](prime_sd.md);
the 1X, which this page compares against, in [1x.md](1x.md).

## Identity

| | 2X | 1X (for comparison) |
|---|---|---|
| Firmware | `PRIME_210419_2` | `ROD1X_200916_2` |
| `RODIN_SUB` | `P` | |
| Board name (`/sys/kernel/board_name`) | `TOC` | `1X_r1` |
| Device tree model | "mv6270 TurnOn Card-Rev C" (`marvell,mv6270-toc`) | `mv6270-1X` |
| TLI | `3D2XAQ` | `3D1XAH` |
| Kernel | 4.2.8, built 2020-11-24 | 4.2.8, built 2019-01-24 |
| Update folder on a stick | `_update_rodin_prime` | `_update_rodin_1x` |
| RAM | 1 GB | 1 GB |

Stock's own scripts call this hardware **"Prime_r1"**, and the eMMC
board (the 1X's kind) **"Prime_r2"**: `powerkeyd.sh` and
`screen_pwroff.sh` branch on the board name, and anything that is not
`Prime_r2` takes the r1 path. This printer takes the r1 path.

## Storage and boot: a NAND machine

The 2X boots like the DP200 family, not like the 1X.

- **NAND**, eight partitions: `miniloader` (1 MB), `r4` (1 MB),
  `u-boot-env` (1 MB), `boot-logo` (2 MB), `u-boot` (1 MB), `kernel`
  (5 MB), `dtb` (512 KB), `filesystem` (the rest, 500 MB).
- **Root** is UBIFS on `filesystem` (`root=ubi0:filesystem`), mounted
  read-write with `sync`. It is **90 % full: 42 MB free** of 447 MB.
  5 bad blocks, highest erase count 944.
- **U-Boot:** `bootcmd=run nandboot`; the environment is in NAND
  (`/dev/mtd2`). It also has a `load_sdcard` line (`mmc dev 2`, kernel
  and `mv6270-toc.dtb` from partition 2 of a card).
- **No `/userdata`, no `/systemdata`.** The 1X's install places do not
  exist here. `/recovery` (177 MB: `rootfs.tar.bz2`, `app.tar.bz2`,
  `recovery.check.sh`) is a folder inside the NAND root.
- **The factory SD card** (8 GB "SL08G", 2018) is in its socket, as
  `mmcblk0` with four partitions (3 MB, 302 MB, 512 MB, 6.6 GB), and
  is **not mounted** in normal running. Partition 2 is an ext
  filesystem last mounted as `/` in January 2018 (the factory image,
  see prime_sd.md); stock's `recovery.check.sh` and `sd_crypt_util.sh`
  refer to partitions 2 and 3.
- **Power-off (r1 path):** `screen_pwroff.sh` kills the programs,
  remounts `/` read-only and then drives **GPIO 111 low ("Set
  write-protect : GPIOD[15]")**. The 1X's script is 101 bytes and
  does neither.

## Pins that differ from the 1X

Three sources agree: the engine's own table (`engine_initGPIO`,
decoded with sindoh-klipper `tools/sindoh_engine_gpio.py`), the pins
exported in `/sys/class/gpio`, and `/app/pinconf.sh` against
`/app/pinconf_r2.sh`. The 2X engine reads `/sys/kernel/board_name`
(`engine_checkBoardRevision`): "Prime_r2" selects the eMMC board's
pins, anything else the NAND board's. On this printer:

| Engine name | 1X | this 2X | Name in `pinconf_r2.sh` |
|---|---|---|---|
| `gp_En_MainFan[1]` (out) | 112 | **126** | `PSU_O1_FAN_CTRL` |
| `gp_Lock_MainFan[1]` (in) | 114 | **128** | `PSU_O1_FAN_LOCK` |
| `gp_En_PSUFan[1]` (out) | 127 | 127 | `PSU_O2_FAN_CTRL` (r2 branch: 113) |
| `gp_Lock_PSUFan[1]` (in) | 129 | 129 | `PSU_O2_FAN_LOCK` (r2 branch: 115) |
| `gp_extrFilaSensor[1]` (in) | 120 | **134** | `EX_FIL_SEN1` |
| `gp_extrFilaSensor[0]` (in) | 121 | **135** | `EX_FIL_SEN2` |
| power board to SoC (the button) | 116 | **130** | `SoC_I/F_A` |
| `gp_Nozzle_Voltage_On` (out) | 69 | none | |

- All other lines are the same on both: fan locks 216, 224, 161, 217,
  175, 210, 95; nozzle fan enables 188, 225; cartridge filament
  sensors 80, 76; level sensor enable 153; test pin 107; TMC select
  146, 147, 149 and 152.
- The 1X engine (ROD1X_200916) has the PSU fan on 127/129, which is
  the r1 numbering, although the 1X is an r2 board; the 2X engine's
  r2 branch would use 113/115. Not looked into further; on the
  owner's 1X the PSU fan does answer on 127.
- **No pin 69 here.** The 2X engine has no `gp_Nozzle_Voltage_On`, no
  `engine_ifRodin1X`, and the screen has no `nozzle_change.html`
  page (the page that switches that pin on the 1X). Live, GPIO 69 is
  an input that reads high. So on this board nothing in software
  switches the nozzle chips' supply; a Klipper config for the 2X must
  not define that pin.
- `powerkeyd` runs as `powerkeyd 130 158 20 1 1 3000`: the button
  line is 130, the answer line is still 158, and the delay before the
  answer is 3000 ms (r2: 1000).
- (our reading) the block moved on r2 because D30/D31 became eMMC
  lines (`pinconf_r2.sh` comments them "eMMC").

### Live pin state, stock idle (GPIO block registers, read 2026-11-28)

- **All eight motor driver enables are outputs and high** (drivers
  off): 56, 164, 170, 38, 53, 44, 96, 50, the order the 1X's
  microcode sets them up in. The 1X uses five of them (164, 170, 38,
  44, 50); 56, 53 and 96 are the three the second head adds.
- The pins next to each enable are driven as on the 1X (x+1 low, x+2
  high), and so are the pairs 193/194, 195/196, 198/199, 200/201,
  204/205, 100/101.
- Outputs here that the 1X does not drive: **126** (the fan enable
  above) and **138** (high; use not known). **111** is an output and
  high: the "write-protect" line stock drops at power-off.
- Both nozzle fan enables (188, 225) and the fan enables 126, 127 are
  low at idle.

### Live PWM blocks, stock idle (read 2026-11-28)

Block numbers as on the 1X (block n at 0xF9304000 + n * 0x100; high
count at +8, low count at +0xC).

| Block | High / low | What |
|---|---|---|
| 5 | 110 / 890 | nozzle heater, running (stock keeps a little heat on at idle) |
| **25** | 109 / 891 | **the second nozzle's heater**: idle on a 1X, running here |
| 28 | 169 / 831 | bed heater |
| 10 | 50 / 50 | power supply fan at 50 % (1X: 80 %) |
| 20 | 80 / 20 | back right exhaust fan at 80 % |
| 2, 14, 22 | 0 / 100 | part cooling fan, and the two blocks that did nothing on the 1X: configured, off |
| 29, 30, 31, 32, 21 | 100, 140, 130, 150, 109 of 200 | motor current references X2, Y, Z, E, C: 100 + the database offsets (0, +40, +30, +50, +9) |

| 19 | 15 / 235 | beeper block (period 250), stopped |

## Same hardware underneath

- **The live device tree is the 1X's, node for node** (481 nodes
  with a `compatible`; same addresses, same status), with one
  difference: `nand@d4283000` is enabled here and disabled on the
  1X. Six stepper blocks, the two UPC cores, the PWM, ADC and sensor
  blocks, six I2C adapters and the UARTs are all where the 1X has
  them.
- **Motion cores:** the engine carries its own two programs
  (`io_ucode_data_H` 18,824 B, `fm_ucode_data_H` 32,692 B; the 1X's
  are 18,444 and 32,632). They are a later build of the same code:
  every hardware address in them is one the 1X's programs use, plus
  one more block in the FM program (0xF9306000). Their start-up has
  not been emulated yet.
- **TMC drivers:** the engine holds `ttyS2` with equal byte counts
  both ways (144/144), as on the 1X. The drivers have not been read
  back (that needs the stock program stopped).
- **Nozzle chips:** the engine opens `/dev/i2c-2` and `/dev/i2c-4`
  for them, as on the 1X. Neither bus had a single interrupt 19
  minutes after power-on, so this boot the chips had not been read.
  `i2c-1` and `i2c-5` had 64 interrupts each (our reading: the two
  cartridge chips); `i2c-3` is the touch controller. No bus was
  probed from our side.
- **Programs:** `UIManager`, `appBrowser` on
  `/app/SVN_GUI/home.html`, the motion program, `powerkeyd`,
  `lighttpd`, `mjpg_streamer` on 8080; the same ports listen (80,
  8080, 9100, 35345, 1337, UDP 161). The binaries are later builds
  (`upc_6270.ko` is 56 bytes longer).
- `/boot` holds five device trees. The one in use is
  `mv6270-toc.dtb`; **`mv6270-Prime-r2.dtb` is byte for byte the 1X's
  `mv6270-1X.dtb`** (same md5), so the 1X board is the "Prime r2"
  board under another name.
- USB: the same webcam (`0c45:6341`), audio (`0572:143b`) and Wi-Fi
  (`1286:2040`) devices as the 1X, on other hub ports.

## Settings database

`/app/nvram/karas.db` has the 1X's tables plus two
(`CONF_DEVELOPER_OPTIONS`, `CONF_ENGINE_GEAR_RATIO`, the latter all
empty). As on the 1X, row 4 of each engine table is this machine
family's; rows 1 to 3 are other models'. **Every engine setting in
row 4 is the same as on the owner's 1X** except what is calibrated
per printer:

| Setting (row 4) | 1X | 2X |
|---|---|---|
| `CONF_MACHINE_OFFSET.HomeZOffset` / `HomeZOffset_NZ2` | 763 / 763 | 3213 / 3249 |
| `NZ1_CleaningGap` / `NZ2_CleaningGap` | 0 / -517 | 1933 / 1969 |
| `X2_AXIS_COMPENSATION` / `Y_AXIS_COMPENSATION` | 0 / 0 | -56 / 32 |
| `CONF_ENGINE_LEVELING` `X2_lvPos`, `X3_lvPos`, `Y1_lvPos` | -320, 18560, 16080 | -240, 18480, 15919 |
| `CONF_ENGINE_LEVELING.ifActiveLevel` | 1 | 0 |
| `CONF_ENGINE_OFFSET.gapAdjust` / `_NZ2` | 1792 / 1792 | 0 / 0 |
| `CONF_ENGINE_PWM.MOTOR_PWM_ZOFFSET` | 40 | 30 |

So the motion numbers worked out for the 1X (speeds, accelerations,
temperatures, the cleaning and loading routines:
[1x_stock_routines.md](1x_stock_routines.md)) are the 2X's too.
(our reading) `HomeZOffset` and `HomeZOffset_NZ2` are the two
nozzles' own Z zero, 36 pulses apart on this printer, and the
`_AXIS_COMPENSATION` values are the second nozzle's X and Y offset
from the XY calibration.

## Two heads: what the engine does

Read from the 2X engine's messages and calls (the same routines are
in the 1X engine, unused there). Not watched on the machine yet.

- **Which driver belongs to which head** (from the masks the engine
  passes to `StepperMotorHolding`, "MotorHolding %08X->%08X"; the
  bit-to-pin table is the FM microcode's, [1x.md](1x.md)):

  | Mask | Bits | Driver enables | Meaning |
  |---|---|---|---|
  | 0x00000107 | 8, 2, 1, 0 | 164, 38, 170, 56 | X2, Z, Y, X1: the axes |
  | 0x0010010F | + 3, 20 | + 53, 96 | axes + head 1's extruder and cartridge feed |
  | 0x00200117 | + 4, 21 | + 44, 50 | axes + head 2's extruder and cartridge feed |
  | 0x0030011F | all | all eight | |
  | 0x00100008 / 0x00200010 | | 53, 96 / 44, 50 | one head's extruder with its cartridge feed |

  So **head 1 (X1, the right one) is X enable 56, extruder 53,
  cartridge feed 96**; head 2 (X2, the left one, the 1X's only head)
  is 164, 44, 50, which is what the 1X uses. (our reading) With six
  stepper blocks for eight drivers, the two extruders share one step
  generator and the two cartridge feeds another, and the enable
  picks which motor turns; X1 and X2 have their own, since both
  move in tandem mode.
- **Homing order avoids a crash** (`engine_initGoX1X2`): it looks at
  both X home sensors first. Both at home or both away: X1 first,
  then X2. Only one at home: the other one first.
- **Tool change** is `T0`/`T1` (also `M135`). The first change does a
  cleaning; later ones a shorter one that depends on the material
  ("PLA/ABS/PVA" or "Flex"); a "declaration" `T` before the first
  move is skipped. After a change the next nozzle is primed
  ("need insert 14.5mm" / "12mm", "Injection 2mm" / "1mm").
- **Second nozzle offsets** (`engine_nozzleX2_Compensation`): when
  nozzle 2 becomes active the engine makes relative moves in X (of
  the X2 carriage), Y and Z ("Compensation"), and undoes them
  ("Release") when nozzle 1 takes over. The Z part is the difference
  of the two nozzles' Z offsets ("Z1Offset ... Z2Offset ... Diff").
- **`M605 S2` is "tandem mode"**: both heads print the same thing
  side by side (`engine_moveToXTandemPos` moves X1 and X2 into place;
  Z uses the mean of the two nozzle offsets). `T0`/`T1` are refused
  in tandem mode. Any other `M605` is single mode.
- **Nozzle calibration on the screen:** XY prints a pattern and asks
  for "the number of the horizontal and vertical lines that appear
  as straight lines" (1 to 11); Z is its own page with a value per
  nozzle; a service page resets both.

## The stock screen app

The 2X and 1X screens are one code base. The 1X's pages are the 2X's
with the second nozzle commented out: 93 of 97 pages have the same
names, and the message files differ by a single key.

- Only on the 2X: `sp_cartridge_2`, `sp_filament_2` (service history
  for nozzle 2), `sp_setting_preheat_3` (preheat for PVA+),
  `sp_setting_wifi` (service switch for Wi-Fi). Only on the 1X:
  `nozzle_change`.
- What the 2X pages add: a nozzle 1 / nozzle 2 selector on the move,
  extrude and Z offset pages; two nozzles and two cartridges on the
  status page; a cartridge selection page in front of load and
  unload; a nozzle selection in front of nozzle replacement.

## Where a hook can live

- Stock's stick update is the DP200 family's: `auto_update.sh` runs
  every `unmistakable*` script in `_update_rodin_prime` on the stick
  (how the survey and the remote shell ran). It refuses a firmware
  older than 180720 ("eMMC Prime and PMP").
- `/etc/inittab` runs `/etc/init.d/rcS`, which runs the `S??` scripts
  in `/etc/init.d` (S01 to S59 are present), then the console login
  runs `/run.sh` as on the 1X. So the 1X's hook file
  (`/etc/init.d/S99klipper`) has a place here too, but on this
  machine it is a write to the NAND root.
- `run.sh` is one script for both boards: it runs `pinconf.sh` or
  `pinconf_r2.sh` by board name, loads `/app/upc_6270.ko`, and on r1
  starts `/recovery/recovery.check.sh` (three passes) around
  `UIManager`; `recovery_watchdog.sh` is not started on r1.

## Stock's self-repair on this board (read 2026-11-28)

On the NAND board the recovery logic is `/recovery/recovery.check.sh`
(version 0.27; `/app/recovery.check.sh` is the eMMC board's and skips
its file system check here: "ignore fsck due to nand board").
`run.sh` starts it three ways: `--snmplib`, `--prior` (before
`UIManager`) and `--post` (after). What matters for anything that
takes over from stock:

- **A watcher checks every 60 s that `appBrowser`, the motion program
  and `UIManager` are running** (`--post-process-integrity`). The
  first time one is missing or a zombie it leaves the loop and:
  1. writes the stamp `/recovery/.allFileCheckNeeded` to the NAND
     root and syncs;
  2. runs the "is a card recovery needed" check (below);
  3. shows "Unexpected Condition / Process is Killed.. / Power Off
     and On" on the screen.
- At the next start `--prior` finds the stamp and reads every file
  of the system ("Integrity Test / Need to check Files.. / do not
  power off"). If the stamp `/recovery/.recovering` is there instead,
  it runs the full repair: unpacks `rootfs.tar.bz2` and `app.tar.bz2`
  from `/recovery` and copies them over `/` with `rsync -c` (no
  `--delete`, so extra files stay, changed stock files are put back).
- **The card recovery check** asks for a recovery from the SD card
  when the root is mounted read-only (`ubifs ro` in `/proc/mounts`),
  when a file in `/recovery` cannot be read, or when `rsync` or `tar`
  do not run. If the card in the socket says it is a "PRIME" card
  (`/app/sd_crypt_util.sh --sdcard-version`) it writes 1 to
  `/sys/kernel/watchdog_reason`, shows "Need Recovery From SD ...
  Power Off and On" and waits forever: the next power-on is a
  recovery boot from the factory card. With any other card it shows
  "Please Use USB Tool to advance Recovery".
- `sd_crypt_util.sh` opens partition 3 of the card as an encrypted
  volume keyed from `/proc/cpuinfo` (`cryptsetup`), and has a
  `do_format` that formats that partition. So a card of ours in the
  socket is something stock may write to.
- `recovery_watchdog.sh` (the 1X's read-only-root watchdog) exists in
  `/app` but is not started on this board.

So on this printer: **stop that watcher before stopping any stock
program, never leave `/` read-only while stock runs, and never write
1 to `watchdog_reason`.** Stopping the motion program with the
watcher alive costs a NAND write and a long file check at the next
start at the least.

## What this means for a Klipper install (our reading)

- The 1X method (our files in `/userdata/klipper`, a boot hook there)
  has no home on this machine: there is no eMMC, and the NAND root
  has 42 MB free. The root of our system has to live on removable
  storage (a USB stick, or a card in the SD socket in place of the
  factory card).
- The DP200 family's lessons apply: NAND writes are the owner's
  call, each one; the U-Boot blocks and environment are never
  written.
- The 1X firmware files should run as they are (same SoC blocks);
  the 1X config needs the pins above changed, pin 69 removed, and
  the second head added. Plan: sindoh-klipper `docs/2x_port_plan.md`.
