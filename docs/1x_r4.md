# 3DWOX 1X: the R4 core on PC_DEBUG2, and how the power board talks to the SoC

Studied 2026-11-24 from the PC only: the strings and code in the 1X's
`/boot/uboot_r4.bin` (copied from the printer, read only). Nothing was
typed on PC_DEBUG2. The firmware itself is Sindoh's and Marvell's and is
not published here.

**Short answer:** the R4 core does not talk to the power board. The
power board is wired to the SoC by two GPIO lines and nothing else
(below). The R4's "power manager" commands are about the SoC's own sleep
states (clocks, DDR self-refresh), not the printer's power supply.

## What is in `/boot/uboot_r4.bin` (5 MB)

| Offset | What | Built |
|---|---|---|
| 0 | Sindoh's **U-Boot 2015.10** for the main cores (Thumb-2, runs at `0x08c00000`) | 2019-03-22 |
| about `0x106000` | The **R4 firmware**: Marvell "g2-r4", ThreadX G5.1.5.0, `PROD=marvell_6270_board_r4 debug` | 2016-11-15 |
| `0x11d34c` | Its **low-power part**: `PROD=marvell_6270_r4_lowpower debug LPP=ARM_R4` | 2016-11-15 |

The line seen on PC_DEBUG2 at power-on (`FW Rev: 20161115 ...
PROD=marvell_6270_board_r4 debug; ASIC_REV: 130`, then `Unittest
commands registered.`) is the R4 firmware's start message
(`FW Rev: %s %s; ASIC_REV: %d; HW: %#x:%x:%x`), so this is the firmware
that runs. It is Marvell's reference firmware for the 88PA6270, built in
debug mode; nothing in it is Sindoh's or printer-specific.

### 2. The `lp>` key menu

Used while the low-power part runs (the chip asleep). Single keys, no
Enter: `x` exit and wake, `q` quick, `! @ # $` debug levels, `A`/`B`/`C`
power traces, `D` and `I` cache flush, **`H` halt**, **`K` kill**, `L`
event log, **`M` modify variables** (system, core and DDR PLLs, clock
dividers), `V` version, `W` WFI skip, `a` alarm, `c` command table, `l`,
`m` memory checksum, `p` pause on power steps, **`r`/`w` read and write
a 32-bit word**, **`'`/`"` the same with the memory protection off**
("be very careful").

**Rule stays: never type on PC_DEBUG2.** Half the commands write memory,
drive pins or halt cores, and a stray key in the `lp>` menu acts at
once.

## How the power board and the SoC talk

The power board's own chip ("PMP" in Sindoh's U-Boot) reads the front
button. U-Boot's board code (`0x08c015b0` on) picks two GPIO numbers by
board name; for `mv6270-1X`:

- **PMP to SoC = GPIO 116** (input): the pulse Linux sees once the
  button has been held about 3 s (sindoh `docs/1x.md`).
- **SoC to PMP = GPIO 158** (output).

Other boards in the same U-Boot (PMP to SoC / SoC to PMP): `mv6270-H`
and `-STF` 165/158, `mv6270-M-H` and `-M-P` 207/208, `mv6270-toc`
130/158, `mv6270-Prime-r2` 116/158 like the 1X.

What each side does with them:

- **U-Boot at power-on:** reads GPIO 116. If it is low (the button held
  while switching on), it prints "Set Recovery mode", drives GPIO 158
  high for 1.5 s, sets it low again and boots the recovery system.
- **Stock Linux, `/app/powerkeyd 116 158 ...`:** on the pulse it runs
  Sindoh's shutdown script, syncs, makes the root read-only, waits 1 s,
  sets GPIO 158 high and halts. The power board then cuts the power.
- Our `x1_web.sh` does the same after a hold of the button.

**GPIO 158 is an answer, not a request (measured 2026-11-27, cold
start, stock's `powerkeyd` frozen):**

| Case | Result |
|---|---|
| 158 high for 5 s, no button hold before it (pin read back high) | stays on |
| 158 high and Linux halted, no button hold (a power-off from our screen's menu) | stays on, halted |
| Button held (116 low for 3.0 s), 158 high 1.5 s after the pulse began | off 1 to 2 s later, the pulse still low at the last log entry |
| Button held, 158 high 5 s after the pulse began (2 s after its end) | off at once |
| Button held, 158 high about 10 s after the pulse began (our 3 s countdown and full shutdown) | off |

So software alone cannot switch the printer off: the power board acts
on 158 only after its own request. How long it keeps waiting is not
measured beyond those 10 s. A log of all eight GPIO level registers
(one pass about every 20 ms) through a tap, a 1 s press and a 3 s hold
showed only 116 react: none of the pins of unknown use (69, 107, 156,
174, 177) changed, and the tap and the 1 s press left nothing. Owner:
holding the button longer cuts the power in hardware even with Linux
halted.

U-Boot's I2C reads go to address 0x50, the 24-series EEPROM in the DIP
socket (byte 0: recovery flag, 1 = boot the recovery from the SD card).
That is not the power board.

**So there is no other channel to the power board:** no I2C, no R4 path,
nothing beyond one input pulse and one output line. Taps, hold length
and "still held" never leave the power board. A real press signal would
take a hardware change (the button's switch also wired to a free SoC
GPIO). With the lines as they are, the software can only act on the
pulse, as our one-hold power-off does (sindoh-klipper
`docs/touchscreen.md`).
