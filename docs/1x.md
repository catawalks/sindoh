# Sindoh 1X: what the model survey found

**Source:** the owner's own 1X, read by the model survey stick
([catawalks/sindoh-model-survey](https://github.com/catawalks/sindoh-model-survey))
four times on 2026-11-20 (v1.0, v1.1 test builds, v1.1). Firmware
`ROD1X_200916_2`, board `1X_r1`, TLI `3D1XAH`. The full reports stay on
the owner's PC (`survey_reports/`), not in this repository. Inferences are
marked "(our reading)". Nothing here was tested with Klipper.

Background from the update files: [other_models.md](other_models.md).

## The machine

| | 1X | DP200 (for comparison) |
|---|---|---|
| SoC | Marvell 88PA6270 "Pegmatite" (DT model `mv6270 TurnOn Card-Rev C`) | 88PA6170 "Gemstone" |
| CPU | 4 x Cortex-A53 (part 0xd03), running 32-bit ARMv7, NEON, VFPv4, AES/SHA/CRC | 2 x Marvell PJ4B |
| RAM | 1 GB (with 270 MB highmem) | 494 MB |
| Kernel | Linux 4.2.8 SMP PREEMPT (2019-01-24), device tree, Linaro GCC 4.9 | Linux 3.2, board file |
| Userland | Buildroot 2016.02, BusyBox 1.24.1, OpenSSL 1.0.2, SQLite 3.10.2 | Buildroot |
| Storage | 8 GB eMMC (6.26 GiB user area), no NAND, no UBI | 256 MB NAND, UBI |
| Root | ext4 on `mmcblk0p2`, 800 MB, **413 MB free** | UBIFS on mtd6 |

## eMMC layout

| Partition | Size | Use |
|---|---|---|
| `mmcblk0boot0`, `boot1` | 4 MB each (read-only) | boot loader; `boot1` also holds the U-Boot env (`/etc/fw_env.config`: two 8 KB copies at 0 and 0x2000) |
| `p1` | 5 MB | raw (our reading: boot logo or loader data) |
| `p2` | 800 MB | root, ext4, kernel and DTB in `/boot` (`uImage`, `mv6270-1X.dtb`) |
| `p3` | 300 MB | `/systemdata`, ext4 |
| `p4` | | extended partition |
| `p5` | 700 MB | recovery root: U-Boot `recoveryboot` loads `/boot/uImage` from `mmc 0:5` |
| `p6` | 4.4 GB | `/userdata`, ext4, **4.1 GB free** |
| `p7` | 127 MB | not mounted |

- U-Boot boots with `bootcmd=run sdcardboot`: `ext2load` of the kernel and
  DTB from `p2`, then `bootm`. A second complete system in `p5` is the
  recovery (`force_recovery=no`).
- (our reading) This is far easier than the DP200: a kernel is a file in
  `/boot` on ext4, not a raw NAND write, and the recovery system stays as
  a fallback. Klipper fits easily, in `/userdata` or the root.

## Motion and peripherals

- **UPC is used.** `upc` (`/app/upc_6270.ko`, 211 KB) is loaded; the stock
  engine program `/marvell_lspsdk_3dp_granite2-debug_stripped.elf`
  reloads it at boot (dmesg: "UPC1/UPC0 device remove" at 14.8 s, then
  "upc start" at 21.9 s, and a UPC1 interrupt). The stock app also has
  `upcLogCap`. (our reading) As on the DP200, motion likely runs on the
  UPC cores, so the Klipper UPC port is the right model, with a new memory
  map.
- **Kernel motion drivers** (Marvell's, out of tree): `stepper_mod_b0`
  (probes motors 0 to 5), `stepper_api_b0`, `dcmotor_6pin` and
  `dcmotor_reg` (seven `dcmotor` blocks at 0xf8140000 to 0xf8146000),
  `dec_pwm` (PWM blocks at 0xf9304000), `dec_adc` (0xf930a000),
  `sensors_gpio`, `wavegen`. The DP200 has none of these as modules.
- **Motor currents:** `CONF_ENGINE_PWM` has the same columns as the
  DP200's. Rows NO=1 to 3 read X -15, Y +15, Z +30, E +50; row NO=4 (the
  one our installer reads) reads **-15, +40, +40, +50**, against Sindoh's
  factory -15, +20, +30, +50 (Prime recovery card, [prime_sd.md](prime_sd.md))
  and the dev DP200's -15, +20, +30, +50. Whether `(100 + offset) / 200`
  is the 1X's current rule still has to be confirmed.
- **Serial:** two UARTs: `ttyS0` (UART1, 0xd4030000) is the console;
  `ttyS2` (UART3, 0xd4018000) is held by the stock engine program
  (256 bytes each way at the survey). (our reading) The engine talks to
  something there: a head board or power MCU.
- **USB:** a webcam (`0c45:6341`, streamed by `mjpg_streamer` on port
  8080), a USB 2.0 hub, the Marvell 8782 Wi-Fi (`1286:2040`, `usb8xxx` +
  `mlan`), a Conexant USB audio device (`0572:143b`, the beeper or speaker
  (our reading)), and a USB device port as a printer gadget
  (`g_printer`/`usb_f_printer`). `ftdi_sio` is loaded with nothing on it.
- **Network:** Ethernet (`stmmac`, `eth0`) and Wi-Fi (`mlan0`).
- **Other:** six I2C buses, a hardware watchdog fed by BusyBox
  `watchdog -t 25 -T 60`, an RTC, SATA (AHCI) and USB 3 blocks unused,
  and the stock laser-printer drivers (`laservideo`, `piedriver`,
  `scanblkdriver`, ...) still loaded (the SoC is a printer chip).
- **Screen:** `/app/appBrowser` (Qt 5 WebKit) on `linuxfb`, touch on
  `/dev/input/event0`, started and watched by `UIManager` and
  `/app/recovery_watchdog.sh`. Killed and restarted by hand, it stuck at
  "Booting: Please wait until booting is complete" until a power cycle
  (survey test, 2026-11-20); never restart it that way.

## Live map over SSH (2026-11-20)

Read-only, from the remote shell (`tools/remote_shell/`), with the stock
system running. Raw output on the owner's PC
(`survey_reports/1x_ssh_map*_20261120.txt`).

**UPC (from the live device tree):**

| | UPC0 | UPC1 |
|---|---|---|
| ITCM | 0xF9800000, 32 KB | 0xF9810000, 32 KB |
| DTCM (shared) | 0xF9880000, 256 KB | same |
| Registers | 0xF9808000 | 0xF9808000 |
| IRQ (SPI) | 204 | 205 |

- Driver `marvell-upc` (`/app/upc_6270.ko`, md5 `8620f61c`; a second
  `upc.ko` in `/lib/modules/4.2.8/extra`, `77776152`), `/dev/upc0`,
  `/dev/upc1`. It exports `upc_read/write_itcm/dtcm`, mailbox, gp status
  and `upc_soft_reset`, like the DP200 driver; the core is called
  "dragonite" in it. Clock gate `ipsbusupcclkgate` at 0xF9080170.
- UPC firmware: `/usr/sbin/UPC_firmware/` with `upc_int.bin` (2760 B),
  `upc_wait.bin`, `upctalk0.bin`, `upctalk1.bin` (about 1.4 KB each) and an
  ELF `upc_start_stop`. These are test programs. The real UPC code is
  built into the engine program (see "Offline study" below).
- **Stepper hardware:** six `stepper-mod-b0` blocks at
  0xF8150000-0xF8155000 (IRQ SPI 176+, `/dev/stepper0`-`5`,
  `/dev/stepper_status`, driver `g2_stepper`), plus seven `dcmotor` blocks
  at 0xF8140000-0xF8146000. The engine program
  (`/marvell_lspsdk_3dp_granite2-debug_stripped.elf`, 44 threads, started
  by UIManager from `/app`) opens `/dev/upc0`/`1` at boot. Later
  correction: it keeps no `/dev/stepper*` or `/dev/mem` open, and the
  stepper blocks are driven by the UPC microcode, as on the DP200.

**Motor drivers: TMC2224 over one UART.** `ttyS2` (UART3, 0xD4018000,
115200 baud, raw) is held by the engine, and its byte counts are equal
both ways (368/368): a single-wire TMC UART that echoes what it sends.
The engine has `tmc2224_readRegister`/`writeRegister`, a
`UART_motorSelect` with GPIO lines `gp_motor_select_0/1/2`, and a factory
check over "X1(0), X2(1), Y(2), Z1(3), E1(4), E2(5), C1(6), C2(7)" (the
1X checks X2, Y, Z1, E2, C2). So one UART reaches up to eight TMC2224s
through a 3-bit select. It also sets a Z `TPWMTHRS` (stealthChop
threshold) and reads `MicroStep`/`Encoder` counts.

**Other devices:**
- I2C: a 24C08 EEPROM at bus 0, 0x50-0x53; the Rohm BU21029 touch
  controller at bus 3, 0x40 (`/dev/input/event0`). The engine also opens
  `/dev/i2c-1`, `-2`, `-4`, `-5`.
- ADC: `dec-adc` at 0xF930A000 (SAR ADC; the heater and thermistor
  inputs, our reading). The engine names `heaterbd1/2`, `heaterex1/2`,
  `thermibd1`, `thermirex1/2`. PWM: `dec-pwm-block` with 19 channels.
- GPIO: 26 lines exported (24 held by the engine, 2 by `powerkeyd`);
  roles in "GPIO map" below.
- Network services: lighttpd :80, mjpg_streamer :8080, the engine on
  :9100 (raw printing) and :35345, UIManager on :1337, SNMP on UDP 161.
- 22 UIO devices for the printer-chip image blocks (JPEG, JBIG, rotate).

## Offline study of the stock binaries (2026-11-20)

Copied read-only over the remote shell (tar over SSH, md5 checked against
the 1X): `/lib/modules/4.2.8/extra`, `/app/upc_6270.ko`,
`/usr/sbin/UPC_firmware`, `/boot/mv6270-1X.dtb` and the engine ELF. They
stay on the owner's PC (`1x_files/`), never in a repository. Read with a
small FDT parser, Python string dumps, and capstone + pyelftools (ARM
disassembly; the engine keeps its dynamic symbol table, so function and
variable names are known). Live reads: GPIO `direction`/`edge` in sysfs,
`/proc/<pid>/fd` and `/proc/<pid>/maps`. No GPIO values, no devmem.

### Motion runs on the UPCs, like the DP200

The engine embeds two UPC programs and loads them at boot
(`upc_driver_init`: "Load IOCode" with `writeFD0_ITCM`, "Load FMCode"
with `writeFD1_ITCM`):

| Array in the engine | Size | Core | Hardware it addresses (literal pool) |
|---|---|---|---|
| `io_ucode_data_H` | 18,444 B | UPC0 | ADC 0xF930A000, PWM 0xF9304000, sensor 0xF9301000, GPIO 0xD4019000, stepper block 3 |
| `fm_ucode_data_H` | 32,632 B | UPC1 | all six stepper blocks 0xF8150000-0xF8155000, PWM 0xF9304000/5000, GPIO 0xD4019000 |

- Both start with the same ARM vector table as the DP200's `io`/`fm`
  microcode (`fm_ucode_data_P` 16,192 B, `RE_analysis/stock_*.bin`), and
  their log strings have the same `[FM]`/`[IO]` style. (our reading) Same
  design as the DP200: FM = motion, IO = heaters, fans and sensors. So the
  Klipper UPC port is the right model for the 1X; what changes is the
  memory map (above) and the stepper block layout (below).
- The host side converts G-code to step pulses (`parseGcode_G0_G1_calcPulse`)
  and sends move and acceleration tables (`upc_setupAccelTbl`,
  `upc_sendAccelHeader`, `UpcSetMachineConstraints`). The parser handles
  G0/G1, G4, G28, G90-92, G200, M2, M72, M82/83, M104/109, M106/107,
  M135, M140/190, M206, M226, M605, M702, T.
- Axis names in the engine: X1, X2, Y, Z, E, C (`StepperHomeX1LongJump`,
  `StepperAbsoluteMoveX2`, `StepperRelativeMoveC`, ...), plus a clutch and a
  solenoid. (our reading) The code is shared with a two-carriage model
  (M605, X2); the 1X's TMC check covers X2, Y, Z1, E2, C2.

### Stepper block registers (stepper-mod-b0.ko)

From `dbg_print_reg` (name, offset as printed by Marvell's driver):

| Offset | Name | Offset | Name |
|---|---|---|---|
| 0x00 | SMC_CFG | 0x6c | OUT_MODE |
| 0x08 | LS_INCR | 0x70 | STEP_INT |
| 0x0c | REG_01 | 0x74 | PWM_T |
| 0x10 | NUM_USTEPS | 0x78 | PWM_P |
| 0x14 | STEP_EN_IDLE | 0x7c | ACC_INCR |
| 0x18-0x38 | TVT_01 ... TVT_16 (9 words) | 0x80 | PWM_M |
| 0x3c, 0x44 ... 0x64 | SEQ_0 ... SEQ_5 | 0x84 | CMD |
| 0x40, 0x48 ... 0x68 | SEQ_0_U ... SEQ_5_U | 0x8c-0xa8 | COM_STAT, COM_PWM_P, COM_ACC_INCR, COM_PWM_M, COM_CMD, COM_STP, COM_TVT, COM_SEQ |
| | | 0xac, 0xb0 | I_EN, I_PEND |
| | | 0xbc | SMC_TRIG |
| | | 0xc0, 0xc4 | REV0, REV1 |

- (our reading) From OUT_MODE to I_PEND this is the DP200's layout moved
  up by 0x28 (DP200: OUT_MODE +0x44, CMD +0x5c, COM_STAT +0x64, COM_STP
  +0x78, I_PEND +0x88; [faster_stepping_plan.md](faster_stepping_plan.md)).
  The 1X block has more words in front (the `_U` sequence words). That
  explains the old note that these names "did not fit" the DP200 block:
  the offsets must be shifted. SMC_TRIG at 0xbc does not follow the shift
  (DP200 +0x8c was our guess, not Marvell's name). Not checked on hardware.
- Block 0 is 0x128 bytes in the DT, blocks 1-5 0x100. Blocks 0-2 have
  pinmux groups of six pads each (`pinmux_stepper0/1/2_pins`, function 2;
  pads 170-175, 176-181, 36-41); blocks 3-5 have none.
- Kernel API: `/dev/stepperN` ioctl and write go straight to
  `stmot_ioctl(motor, cmd, arg)` with commands 0-0x12 (motor 0-9);
  `stepper-api-b0` exports `smot_step_move_abs/rel/cont`, `set_speed`,
  `set_motor_move_params`, `emergency_halt`, u-steps 1/2/4/8/16. The stock
  engine does not use this path (no open fds). Command meanings not
  decoded.

### Heaters and thermistors

- Two lookup tables in the engine, ADC count to milli-°C:
  `adc_temp_mC_lookup_table` (1938 entries, 300 °C at index 0, 100 °C near
  1353, 25 °C near 1861) for the nozzles, `adc_bed_mC_lookup_table` (1667
  entries, 125 °C at 0, 25 °C near 1271) for the bed. Saved as CSV on the
  owner's PC (`1x_files/*.csv`). The index base (raw ADC or offset) is not
  decoded yet; Klipper would need these as `[thermistor]` or
  `[adc_temperature]` points.
- Factory test names: `heaterbd1/2`, `heaterex1/2`, `thermibd1`,
  `thermirex1/2`; tests "Bed thermistor", "Extruder 1/2 thermistor".
- The ADC (0xF930A000) and PWM are driven by the IO microcode, not by the
  host (see above). DT: `dec-adc` instruction0 0x10001, instruction1 2;
  `dec-pwm` 32 channel nodes (0xF9304100 + n*0x100), only channels 6 and
  18 have DT defaults; `dec-fuser` (laser-printer heater block) and
  `dec-sensor` are disabled.

### Engine and UI

The engine talks to UIManager and the other daemons over POSIX message
queues (`/mq_sys_to_ui`, `/mq_ui_to_sys`, `/GCODEParserQ`, ...), not
sockets; no protocol was decoded from strings.

## karas.db

At `/app/nvram/karas.db`, as on every model. It has most of the DP200's
config tables (`CONF_ENGINE_PWM`, `CONF_ENGINE_TEMPERATURE`,
`CONF_ENGINE_LEVELING`, `CONF_MACHINE_OFFSET`, `INST_ENGINE_GENERAL` with
`printingStatus`, ...) plus 1X ones: `CONF_ENGINE_ACTIVELEVELING`,
`CONF_ENGINE_CLEANING`, `CONF_ENGINE_CLEANPIPE`, `CONF_OBJECT_DETECT`,
`CONF_ENGINE_JIGPARAM`, per-material `CONF_ENGINE_NOZZLE_PLUMBING_*`, and
`MCONF_FILAMENT_TYPE`.

## What a Klipper port needs (our reading)

1. **Step generation:** as on the DP200, stock runs motion on UPC1, which
   drives the six `stepper-mod` blocks. So the Klipper UPC port fits, with
   the 6270 memory map (above) and the 1X block layout (register table
   above, DP200 offsets + 0x28). Still open: which block drives which axis,
   and the meaning of SEQ/TVT/OUT_MODE on the 1X (the FM microcode can be
   run in `tools/fmseq.py` like the DP200's).
2. **TMC2224 setup** over `ttyS2` with the 3-bit motor select: Klipper's
   `tmc2208`-family UART code fits, plus the select GPIOs.
3. Heater, thermistor and fan wiring: fan enables and tach inputs are
   mapped (GPIO table); heater PWM channels, ADC channels and the
   thermistor table base still need the IO microcode.
4. A stick install target: `/userdata` has the space; the root is ext4, so
   no UBI work is needed.

The remote shell gives a live view for all of these; nothing that moves
or heats runs without the owner.
