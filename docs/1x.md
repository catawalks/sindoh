# Sindoh 1X: what the model survey found

**Source:** the owner's own 1X, read by the model survey stick
([catawalks/sindoh-model-survey](https://github.com/catawalks/sindoh-model-survey))
four times on 2026-11-20 (v1.0, v1.1 test builds, v1.1). Firmware
`ROD1X_200916_2`, board `1X_r1`, TLI `3D1XAH`. The full reports stay on
the owner's PC (`survey_reports/`), not in this repository. Inferences are
marked "(our reading)". Nothing here was tested with Klipper.

Background from the update files: [other_models.md](other_models.md).

## The machine

| | 1X | DP200 (for comparison) |
|---|---|---|
| SoC | Marvell 88PA6270 "Pegmatite" (DT model `mv6270 TurnOn Card-Rev C`) | 88PA6170 "Gemstone" |
| CPU | 4 x Cortex-A53 (part 0xd03), running 32-bit ARMv7, NEON, VFPv4, AES/SHA/CRC | 2 x Marvell PJ4B |
| RAM | 1 GB (with 270 MB highmem) | 494 MB |
| Kernel | Linux 4.2.8 SMP PREEMPT (2019-01-24), device tree, Linaro GCC 4.9 | Linux 3.2, board file |
| Userland | Buildroot 2016.02, BusyBox 1.24.1, OpenSSL 1.0.2, SQLite 3.10.2 | Buildroot |
| Storage | 8 GB eMMC (6.26 GiB user area), no NAND, no UBI | 256 MB NAND, UBI |
| Root | ext4 on `mmcblk0p2`, 800 MB, **413 MB free** | UBIFS on mtd6 |

## eMMC layout

| Partition | Size | Use |
|---|---|---|
| `mmcblk0boot0`, `boot1` | 4 MB each (read-only) | boot loader; `boot1` also holds the U-Boot env (`/etc/fw_env.config`: two 8 KB copies at 0 and 0x2000) |
| `p1` | 5 MB | raw (our reading: boot logo or loader data) |
| `p2` | 800 MB | root, ext4, kernel and DTB in `/boot` (`uImage`, `mv6270-1X.dtb`) |
| `p3` | 300 MB | `/systemdata`, ext4 |
| `p4` | | extended partition |
| `p5` | 700 MB | recovery root: U-Boot `recoveryboot` loads `/boot/uImage` from `mmc 0:5` |
| `p6` | 4.4 GB | `/userdata`, ext4, **4.1 GB free** |
| `p7` | 127 MB | not mounted |

- U-Boot boots with `bootcmd=run sdcardboot`: `ext2load` of the kernel and
  DTB from `p2`, then `bootm`. A second complete system in `p5` is the
  recovery (`force_recovery=no`).
- (our reading) This is far easier than the DP200: a kernel is a file in
  `/boot` on ext4, not a raw NAND write, and the recovery system stays as
  a fallback. Klipper fits easily, in `/userdata` or the root.

## Motion and peripherals

- **UPC is used.** `upc` (`/app/upc_6270.ko`, 211 KB) is loaded; the stock
  engine program `/marvell_lspsdk_3dp_granite2-debug_stripped.elf`
  reloads it at boot (dmesg: "UPC1/UPC0 device remove" at 14.8 s, then
  "upc start" at 21.9 s, and a UPC1 interrupt). The stock app also has
  `upcLogCap`. (our reading) As on the DP200, motion likely runs on the
  UPC cores, so the Klipper UPC port is the right model, with a new memory
  map.
- **Kernel motion drivers** (Marvell's, out of tree): `stepper_mod_b0`
  (probes motors 0 to 5), `stepper_api_b0`, `dcmotor_6pin` and
  `dcmotor_reg` (seven `dcmotor` blocks at 0xf8140000 to 0xf8146000),
  `dec_pwm` (PWM blocks at 0xf9304000), `dec_adc` (0xf930a000),
  `sensors_gpio`, `wavegen`. The DP200 has none of these as modules.
- **Motor currents:** `CONF_ENGINE_PWM` has the same columns as the
  DP200's. Rows NO=1 to 3 read X -15, Y +15, Z +30, E +50 (the dev DP200:
  -15, +20, +30, +50). The same rule our installer uses (row NO=4,
  `(100 + offset) / 200`) still has to be confirmed for the 1X.
- **Serial:** two UARTs: `ttyS0` (UART1, 0xd4030000) is the console;
  `ttyS2` (UART3, 0xd4018000) is held by the stock engine program
  (256 bytes each way at the survey). (our reading) The engine talks to
  something there: a head board or power MCU.
- **USB:** a webcam (`0c45:6341`, streamed by `mjpg_streamer` on port
  8080), a USB 2.0 hub, the Marvell 8782 Wi-Fi (`1286:2040`, `usb8xxx` +
  `mlan`), a Conexant USB audio device (`0572:143b`, the beeper or speaker
  (our reading)), and a USB device port as a printer gadget
  (`g_printer`/`usb_f_printer`). `ftdi_sio` is loaded with nothing on it.
- **Network:** Ethernet (`stmmac`, `eth0`) and Wi-Fi (`mlan0`).
- **Other:** six I2C buses, a hardware watchdog fed by BusyBox
  `watchdog -t 25 -T 60`, an RTC, SATA (AHCI) and USB 3 blocks unused,
  and the stock laser-printer drivers (`laservideo`, `piedriver`,
  `scanblkdriver`, ...) still loaded (the SoC is a printer chip).
- **Screen:** `/app/appBrowser` (Qt 5 WebKit) on `linuxfb`, touch on
  `/dev/input/event0`, started and watched by `UIManager` and
  `/app/recovery_watchdog.sh`. Killed and restarted by hand, it stuck at
  "Booting: Please wait until booting is complete" until a power cycle
  (survey test, 2026-11-20); never restart it that way.

## karas.db

At `/app/nvram/karas.db`, as on every model. It has most of the DP200's
config tables (`CONF_ENGINE_PWM`, `CONF_ENGINE_TEMPERATURE`,
`CONF_ENGINE_LEVELING`, `CONF_MACHINE_OFFSET`, `INST_ENGINE_GENERAL` with
`printingStatus`, ...) plus 1X ones: `CONF_ENGINE_ACTIVELEVELING`,
`CONF_ENGINE_CLEANING`, `CONF_ENGINE_CLEANPIPE`, `CONF_OBJECT_DETECT`,
`CONF_ENGINE_JIGPARAM`, per-material `CONF_ENGINE_NOZZLE_PLUMBING_*`, and
`MCONF_FILAMENT_TYPE`.

## What a Klipper port needs (our reading)

1. The UPC memory map and peripherals on the 6270 (the DP200's
   `upc_fw/probe/` method), with `upc_6270.ko` loaded.
2. What the engine program talks to on `ttyS2`, and how the stepper and
   dcmotor drivers relate to the UPC (does the UPC step the motors, or the
   `stepper_mod` hardware?).
3. Heater, thermistor and fan wiring (the `dec_pwm` and `dec_adc` blocks).
4. A stick install target: `/userdata` has the space; the root is ext4, so
   no UBI work is needed.

A serial console on `ttyS0` (115200) would help with all of these.
